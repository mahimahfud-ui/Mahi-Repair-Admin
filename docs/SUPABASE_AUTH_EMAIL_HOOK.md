# Supabase Auth Send Email Hook — Resend primary, Brevo fallback

**Production Supabase project:** `shwqsljicmhflnvjqjah`  
**Deployed Edge Function:** `send-email-hook` v1  
**Endpoint:** `https://shwqsljicmhflnvjqjah.supabase.co/functions/v1/send-email-hook`

## Delivery path

Supabase Auth creates the verification token/hash and invokes this signed Send Email Hook. The function verifies the Standard Webhooks signature, renders a compact Mahi Repair email, tries Resend first, and uses Brevo only when Resend is not configured or returns a failed response.

- Resend: `POST https://api.resend.com/emails`, using `RESEND_API_KEY`.
- Brevo fallback: `POST https://api.brevo.com/v3/smtp/email`, using `BREVO_API_KEY`.
- Both providers must have the sender domain/address verified.
- The Auth-generated OTP/token hash and action type are preserved. The verification link points to the Supabase Auth verify endpoint and carries the supplied `redirect_to` unchanged as a query parameter. Supabase Auth remains responsible for allowed redirect validation.
- The same endpoint handles both current `user` + `email` hook payloads and older `user` + `email_data` payloads.
- Provider response bodies, OTPs, token hashes, recipient addresses and webhook signatures are never written to application logs.

The function is deployed with `verify_jwt=false` because Supabase Auth sends a signed webhook, not a user JWT. It validates `SEND_EMAIL_HOOK_SECRET` with the Standard Webhooks signature before processing any email. All other application Edge Functions retain JWT verification.

## Required Edge Function secrets

Configure these in **Supabase Dashboard → Edge Functions → Secrets**. Do not put them in GitHub, Render, client-side variables, Android `.env`, or chat.

| Secret | Purpose |
|---|---|
| `SEND_EMAIL_HOOK_SECRET` | Secret generated by Supabase when creating the Auth Send Email Hook; copy the complete `v1,whsec_...` value |
| `RESEND_API_KEY` | Resend API key (primary provider) |
| `BREVO_API_KEY` | Brevo API key (fallback provider) |
| `AUTH_EMAIL_FROM` | Verified sender email address, e.g. `auth@your-verified-domain` |
| `AUTH_EMAIL_FROM_NAME` | Optional sender display name; defaults to `Mahi Repair` |
| `RESEND_EMAIL_FROM` | Optional Resend-specific verified from header; defaults to `AUTH_EMAIL_FROM_NAME <AUTH_EMAIL_FROM>` |

The Edge Functions runtime supplies `SUPABASE_URL`. No service-role key is required by this email handler.

Configure both provider keys to enable actual fallback. If either provider is missing, the function can use the other provider but cannot provide two-provider failover.

## Connect the hook in Supabase Auth

After the secrets above are saved:

1. Open **Supabase Dashboard → Authentication → Hooks**.
2. Add a **Send Email Hook** and choose HTTPS.
3. Set the URL to the endpoint shown at the top of this document.
4. Generate the webhook secret in the dashboard.
5. Save that exact complete secret as `SEND_EMAIL_HOOK_SECRET` in Edge Function secrets.
6. Save/enable the hook and confirm its status in the dashboard.

Do not configure `verify_jwt=true` for this function; the handler authenticates the request through the signed webhook headers. Do not remove signature verification or make this a public unauthenticated email-sending API.

## Acceptance test

No test or sign-in emails were sent during deployment. After the sender/domain, provider keys and Auth hook are configured by the project operator:

1. Use one explicitly authorized Member account to request a normal OTP.
2. Confirm the email arrives through Resend.
3. Temporarily cause a controlled Resend failure in a non-production environment and confirm Brevo receives the fallback request.
4. Confirm both OTP code and magic-link action flows preserve the Auth token/action/redirect.
5. Confirm invalid webhook signatures receive HTTP 401 and missing hook/provider configuration fails closed.
6. Check logs only for provider outcome/status; never log OTP, token hashes, email content or credentials.
